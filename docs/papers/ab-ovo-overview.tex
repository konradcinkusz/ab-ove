\begin{abstract}
\noindent
ab-ovo is a learning platform built around a book of 47 programmed-learning programs, in
English and Polish, together with that book's computer exercises. This document is a
project overview: what the system is, what it deliberately is not, what exists in the
repository today, and what is planned. It is not a research paper and reports no result.
Every statement in it is drawn from the repository's markdown documentation, which is the
source of truth; where the two disagree, the markdown is right. Its figures are the
repository's own diagrams, rendered from the same sources GitHub renders.
\end{abstract}

\section{What ab-ovo is}

The book it encapsulates is built on a mechanism that paper cannot enforce. A Stroud frame
asks the reader for something \emph{before} it tells them anything, and the next frame opens
with the answer they were supposed to have written. A reader who skims gets nothing from
that structure, and a printed page has no way to notice.

ab-ovo is the software that does notice. A reader reads a frame, commits an answer, and
reveals the next frame, which opens with the answer. The reveal is a navigation rather than
a toggle, so the answer to the frame on screen is rendered by the request for the next one
and by nothing before it: it is absent from the document rather than hidden in it, and a
reader who opens the inspector finds nothing. Where a frame asks for something, a worksheet
sits below it --- a line to answer on, a pad that evaluates arithmetic, a canvas to sketch
on --- and all three are optional and local to the reader's browser. The book's computer
exercises are worked in a separate lab pane, in which Python runs in the reader's own
browser; they left the reading loop deliberately, because a reader of a mathematics book
should not have to write code to answer a frame.

\begin{figure}[ht]
\centering
\includegraphics[width=0.78\linewidth]{\dgm{b1-reader-loop}}
\caption{The reader loop. Every box runs with no account and no backend; the two dotted

The product's first requirement constrains everything else in this document: \textbf{the
reader loop works with no account and no backend.} Frames are served with the site as a
versioned content bundle, the exercises run client-side, and nothing a reader writes on a
frame is stored anywhere but their own browser. An account adds synchronisation of the
reader's place between machines, and nothing else.

\section{What it deliberately is not}

The system collects outcomes, and outcomes about learning drift towards becoming outcomes
about learners, because that is the easier number to produce and the one that looks like
progress. The project's answer is an anti-goal stated at the top of the README, above the
features, and enforced by an architectural absence rather than by policy:

\begin{quote}
The instrument measures \textbf{the book}, never the reader.
\end{quote}

The useful question it answers is \emph{where is this book wasting the reader's time}, not
\emph{which reader is worst}. Concretely, and in a form that a search of the code can
falsify: there is no per-reader view and adding one is not planned; there is no endpoint
whose route or query parameter names a person; and there is no table from which a per-reader
score could be built. Outcomes are recorded against a frame in a bundle version, an attempt
and a check run --- the artifact, never the person --- and the outcome row carries no
identifier and no timestamp, because rows whose times run consecutively over one program
reconstruct a session without naming anybody.

The reader's place in the book is the one thing this estate stores about a person, and it
says where they are and never how they did. Three mechanical rules hold each table rather
than a promise: a closed column list, so a measure of a reader breaks the build; every key
and index leading with the reader on one table and with the bundle version on the other; and
a query that does not pin exactly one of those refused at run time, before the ORM compiles
it. Each was watched refusing something before it was believed.

The reader is also told what the absence costs them, which is the half an architectural
absence cannot deliver on its own: because an outcome carries no reader, nothing can find
the rows that were theirs, so deleting an account cannot retract a contribution already
folded into a rate. The deletion screen says exactly that, beside what the deletion does
remove.

Two further refusals are recorded as decisions rather than left as preferences. No language
model is called anywhere in the reader loop: the comparison against the next frame is the
teaching, and a model's judgement would carry its own error rate into evidence used to
revise a book. And there is no gamification, because a streak is a reason to move a number
that is not learning.

\section{Status: nothing is deployed}

The repository stands at \emph{builds, tests green, images build}. There is no running
instance, at any address, for anybody. Four \texttt{fly.toml} files describe a topology that
has never been applied, and neither container image has ever been published.

What exists is the reading surface over the whole book: every program in both editions, one
frame a screen, with the book's own prose and mathematics; a pager pinned to the bottom of
the screen with a labelled \emph{Previous} and \emph{Next}, and between them the position,
which opens a map of the program; and a worksheet on every frame that asks for something. Behind it: an API, a web application whose landing page is the index of programs,
a Playwright acceptance suite, and the CI gates that would catch a regression in any of it.

The domain model is small and it arrived late on purpose. Entities invented ahead of the
ticket that needs them are code the first real ticket deletes, so the persistence context
held none until synchronisation needed one. It now holds the reader's place in the book, and
the tally of outcomes against a frame --- and nothing else.

The HTTP surface is organised by authorization rather than by feature, and the composition
root reads as a manifest of it. A public group carries readiness, liveness and a service-info
endpoint describing the deployment. An authenticated group carries the reader's own place in
the book, including its deletion. An administrative group carries the rates the author's view
reads. A fourth group is not a fourth member of that triad: it carries the one anonymous
write --- an outcome --- because consent is not an account and an instrument that required a
token would measure the book as experienced by account-holders and call it the book. It takes
the explicit rate limit the authenticated group takes rather than falling through to the
global one, since a probe that gets rate-limited takes a machine out of rotation.

\section{Architecture, and where it departs from the constitution}

The repository is built against a reference architecture held in a separate standards
repository, and \texttt{docs/architecture/00-ARCHITECTURE.md} walks its fifteen principles
against this tree --- referencing the constitution rather than copying it, because a copied
principle is a second copy that goes stale.

Three properties are worth naming in an overview. Optional integrations \textbf{degrade
visibly}: a deployment with no credentials at all starts, serves, and names what it does not
have, in three renderings produced from one source. The shared kernel is held to plumbing by
two mechanisms rather than by prose --- a size gate in CI and an architecture test asserting
that it references no service type and declares no persistence model. And no address is
compiled into any artifact: the frontend reads its configuration at request time, so one
image serves every environment.

That document also carries a \textbf{deviation register}, in which every row has a date, a
reason and an exit condition. What is recorded there today: dependency version automation
declared and switched off; a size gate counting code lines rather than raw lines, so that a
principle requiring reasoning in comments does not spend the budget of a principle capping
size; Python in the browser, which the standards do not evidence; a repository name that is a
typo and a system name that is not; one Aspire API marked evaluation-only, used in a
development-only file; a secret-scan mirror script that is not one-to-one with its CI job; and
a content bundle compiled here from the book at a pinned revision, because no release of the
book carries one yet. That last exit condition is the plainest in the register: the first
release that carries a bundle.

A deviation with no exit condition is a drift rather than a decision, which is why the
column exists.

\section{The plan}

Five phases, ranked in \texttt{docs/ux/UI-UX.md} so that a delivery session picks up a decision
rather than re-deriving one. The earlier phases have landed; the list is kept in its original
order because the reasoning for the order is the useful part of it.

\begin{enumerate}[leftmargin=2em,itemsep=2pt]
  \item \textbf{The lab pane.} The exercises, in the browser. The largest piece that needs
        neither a backend nor the content bundle, which is why it is first.
  \item \textbf{The content schema and the frame view.} Its second half was \emph{blocked} on
        the book publishing a content bundle --- the plan's only external dependency --- and
        was unblocked by compiling one here instead, at a pinned revision, with the book's own
        compiler and its own cross-check. That is a deviation with an exit condition rather
        than a resolution of the dependency. The fixture written for the first half stays, as
        the unit tier's control: a test whose input is the thing under test proves less.
  \item \textbf{Progress and accounts.} Local progress first; an account synchronises it.
  \item \textbf{The instrument.} Opt-in, versioned consent; outcomes against artifacts; every
        rate carrying its interval.
  \item \textbf{The open-source edition.} A one-time, irreversible gate, ordered by
        irreversibility, in which a full history scan for secrets blocks every other item.
\end{enumerate}
