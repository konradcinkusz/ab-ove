# Two surfaces proposed, checked against what `main` already decided

**This is an evaluation, not a decision, and it commits nothing.** A Polish-language sketch
for two learner-facing surfaces — a Web reading loop and an MCP tutor agent, over one shared
core — arrived in conversation on 2026-09-20. It is not committed anywhere in this
repository. Every row below was checked against `origin/main` at `b220847` on that date. A
row marked **Yes** or **Partial** still costs its own ADR before anything is built
([ADR-0001](../adr/0001-record-architecture-decisions.md)): this document sorts the
proposal, it does not adopt any of it.

## Is any of this a real improvement?

Partly. The MCP-side instincts are sound, and in one place — the reveal gate — already
exceeded by what shipped: the proposal asks for a server that refuses to leak an answer, and
the real server does better than that, because the answer to step *k* doesn't exist as a
separate field to leak in the first place. Several Web-side asks — the auto-switching
Answer/Lab panel, no calculator, eager Pyodide with a progress bar, phone tabs, a
Workbox-cached reading surface — don't describe something unbuilt. They describe something
this repository tried, measured, and reversed within the last two days
([ADR-0039](../adr/0039-a-frame-accepts-the-readers-answer-as-a-commitment.md),
[ADR-0040](../adr/0040-the-python-lab-leaves-the-reader-loop.md),
[ADR-0042](../adr/0042-the-evaluator-is-a-calculator-not-a-cas.md)). Building them now would
be a regression against real usage measurement, not an improvement.

A handful of ideas hold up on their own merits, independent of the rest of the proposal: a
Zeszyt-style personal history with export, MCP elicitation as a stronger answer to "who
actually answered", and finishing the `@ab-ovo/web-kit` extraction the docs already call
for. One idea — a third "auto-MCP" outcomes bucket — is valuable in principle and genuinely
hard: it isn't unbuilt so much as fenced off by a privacy invariant that three separate
mechanisms enforce at runtime, and adopting it costs a real design, not a new enum value.

**Verdict key** used in every table: **Yes** — worth building. **No** — already tried,
measured, and reversed, or refused by a standing boundary. **Partial** — worth it only under
a stated condition. **Open** — genuinely undecided; needs design work before it's buildable
either way.

## Open questions

Three items above are marked **Open** for a reason stronger than "not built yet" — each
needs a real design decision, not a task:

1. **Row 15 — an auto-MCP outcomes channel.** Is it worth designing an anonymization scheme
   that could satisfy ADR-0009 §1's own test, and what would an MCP-origin outcome look like
   that still carries no reader, user or author identifier — not a column, not a hash, not a
   join away?
2. **Row 14 — MCP elicitation.** Worth prototyping against at least one host that supports
   it; needs a decision on what the fallback contract stays for hosts that don't.
3. **Row 7 — Zeszyt/export.** Does a reader-owned, local, non-scored history reconcile with
   ADR-0017/0039's "holds nothing worth scoring" stance on its own, or does the *export*
   half specifically need its own carve-out argument (an exported file is a copy that has
   left the guarantees of "local-first" the moment it's saved elsewhere)?

None of the three has an answer here. Each is a candidate for its own ADR, written by
whoever decides to pursue it.
